Working on DIMS

Integration workflow

All code lives in one repository. Studies pin a released version of it. Updating a study is a version bump, not a merge.

RepoRole
dimsall code — core, tabs, analyses, builder; released as tags
case reposone study each: config.json, data, a pinned vendor/dims-core
.githubone copy of every CI job, called by the rest

Lifecycle of a change

  1. Open a pull request against dims

    CI checks Python and JavaScript syntax, validates config.json against the shared schema, runs the analysis and dashboard test suites, and guards file sizes.

  2. Merge

    The single approval point — and now there is only one copy of the code to approve.

  3. Release a tag

    When the change should reach studies.

  4. Studies update themselves

    A bot opens a pull request in each case repo bumping the pinned version and refreshing the vendored copy. CI there verifies the copy matches the release exactly.

There is no step in which anyone copies a file between repositories.

Adding something

Adding a tab or an analysis must not require editing a file that already works — they register themselves. Read the one relevant contract:

  • a tab → docs/contracts/tab.md
  • an analysis → docs/contracts/step.md
  • a new study → docs/contracts/case.md
Human-subject data. Every study declares public or private in dims-case.json, enforced by commit hooks and CI rather than by memory. See the data-visibility contract before working on a study that holds recordings of people.
