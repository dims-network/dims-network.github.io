Getting started

Architecture

All DIMS code lives in one repository. Each study — each recording session, each experiment — lives in its own small repo holding only its configuration, its data, and a pinned version of that core.

How a dashboard works

A deployed dashboard is one small web page with no build step. It reads a config.json (which videos and analyses to show) and the matching data files, and draws everything you see. The one idea to remember: pick a moment in time, and every panel updates to that moment together — the charts, the videos, and the transcript all stay in sync.

dims-core.js is the conductor. It loads the data, keeps the timeline, and tells everything else which moment to show. It does not know what a recurrence plot is, or what ELAN is.

Tab modules do the drawing — one file per tab, in packages/dims-tabs/. Each announces itself to the core and says under what conditions it applies (“show me only if this study has cross-wavelet results”). Delete the file and the tab is gone; add one and it appears. Nothing else changes.

That applies to the built-in tabs too, not just add-ons. It has to: if the mechanism only carried third-party tabs, it could quietly break and nobody would notice until an outside contributor tried to use it.

video-component.js is the one small React piece. The core hands it a video and a time window; it plays just that segment and loops it. In short — the core decides which moment to show, and the tabs and video know how to show it.

One core, many studies

          dims-network/dims                # all the code, released as versions
       core · tabs · analyses · builder
                     │
        pinned and vendored into each study
                     │
      ┌──────────────┼──────────────┐
  case-demo      case-ortho     case-karnatak
  config + data  config + data  config + data (private)

A study repo holds no code of its own. It names a core version in dims-case.json, and a copy of that exact release sits in its vendor/ directory. Continuous integration checks that the copy still matches the release, so hand-editing it is a build failure rather than a silent fork.

Updating a study is therefore a version bump, not a merge: a bot opens a pull request changing the pinned version and refreshing the vendored copy.

Why vendor a copy instead of loading from a CDN? Because these dashboards accompany published research and need to still work in ten years, on a machine nobody maintains, possibly with no network. A self-contained repository can be archived and given a DOI. A link to someone else's server cannot.

What replaced the old model

Until September 2026 the code lived in five repositories kept in step by hand, with one of them nominated as the source of truth. It did not hold, and the failure was measurable: three unrelated git histories, four different copies of the frontend ranging from 2,136 to 2,500 lines, and no single repository containing every feature. One fork carried the only correct wavelet-coherence calculation for months while four others shipped a version that measured signal power instead — not because anyone was careless, but because there was no mechanism for a fix to travel.

The rule is now structural rather than remembered: there is only one copy of the code, so there is nothing to keep in step.

Code, data, and privacy

Every study declares whether its data is public or private, in dims-case.json. It is a decision the researcher makes and records — never something inferred from repository settings, which anyone can change later without knowing what is inside.

  • Public — data is committed alongside the config, and the dashboard publishes to GitHub Pages.
  • Private — the data lives outside the repository entirely. Commit hooks refuse to stage it, CI fails if any of it is ever tracked, and CI also fails if the repository is made public while the study still says private. The dashboard runs locally against the real data; only a manifest of filenames and checksums is committed.

Going public is an explicit, checklisted transition — anonymise, verify frame by frame, then flip the declaration — never a side effect of something else.

The Python side

Analyses are a pip package, dims-analysis. Each analysis is a small class that says which config key switches it on and where its output goes; the runner discovers them rather than listing them. An analysis published in a separate package joins the pipeline with no change to DIMS at all, which is how work from other toolboxes is meant to arrive.
